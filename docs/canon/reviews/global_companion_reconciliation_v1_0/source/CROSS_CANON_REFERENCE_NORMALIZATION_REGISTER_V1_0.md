## 2. Application Rule

A normalized reference changes the cited authority name, not the historical filename or checksum of the source artifact. Historical files remain preserved. New and revised documents must use the current canonical reference unless explicitly discussing a historical version.

## 3. Ambiguity Rule

Where a legacy title may refer to a distinct implementation standard rather than constitutional canon, the author must identify the intended artifact and may not silently map it.

## 4. Usage Examples

- A new plugin-governance document must cite the Master Claims, Disputes, and Authority Model V2.0 rather than the legacy Claims and Retention title.
- A security document may describe privacy-protective safeguards, but it must cite the Privacy and Data Protection Model V2.0 for processing rights and lawful-basis rules.
- A permission document must cite the Agreement, Consent, and Authorization Model V2.1 for the consent record and lifecycle, while retaining permission ownership over enforcement.
- A provider-specific implementation plan may name a vendor, but constitutional adapter rules must cite the External Architecture and Adapter Model V2.1 and current preferences must cite the Approved Provider Strategy Register V1.0.
- A historical audit may quote an older filename exactly when the historical reference is material, but it must identify the current controlling successor.

## 5. Review Rule

The register must be reviewed whenever a canonical document is renamed, versioned, split, consolidated, superseded, or assigned a new constitutional owner. Broken-reference scans must use this registry as a normalization dictionary before treating a legacy title as a missing document.

## 6. Authority Boundary

This registry corrects references. It does not amend the substance of a cited canon, alter a historical checksum, authorize adoption or lock, or create implementation and production authority.
