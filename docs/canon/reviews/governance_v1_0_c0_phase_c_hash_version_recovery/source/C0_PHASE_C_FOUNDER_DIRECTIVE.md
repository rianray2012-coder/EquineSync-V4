## 1. Purpose

Codex is authorized to conduct a controlled source-forensics and lifecycle-recovery review for the nine C0 Track C constitutional rows.

The purpose of this phase is to:

1. recover the exact historical bytes identified by the C0 baseline;
2. verify each recovered source against its expected SHA-256;
3. preserve the current repository artifact without overwriting it;
4. compare the expected source with the related current repository artifact;
5. determine whether the current artifact is:

   * byte-identical;
   * a formatting-only derivative;
   * a corrected successor;
   * a substantive superseding successor;
   * a noncontrolling derivative;
   * an unauthorized modification;
   * a conflicting artifact; or
   * an artifact whose relationship cannot yet be established;
6. prepare a row-specific founder source-identity or succession decision package;
7. determine adoption eligibility; and
8. stop before adoption or lock unless a later, separate founder directive expressly authorizes those lifecycle events.

This is a source-recovery and classification phase. It is **not** a substantive canon-redrafting phase.

## 4. Governing principles

Codex shall apply the following rules:

### 4.1 Exact bytes control evidence

Source identity must be supported by:

* exact bytes;
* independently calculated SHA-256;
* provenance;
* source location;
* chain of custody; and
* comparison against the current repository artifact.

### 4.2 No reconstruction

Codex may not recreate, approximate, redraft, regenerate, or reverse-engineer a missing expected source merely to produce the expected title or version.

A newly generated file can never be represented as the recovered historical source.

### 4.3 Preserve both sides of the comparison

The expected historical source and current repository artifact must both be preserved.

Do not overwrite:

* the current repository artifact;
* recovered historical bytes;
* prior C0 records;
* prior evidence packages;
* earlier founder-approved versions; or
* locked RF or canon artifacts.

### 4.4 Newest does not automatically mean controlling

A newer timestamp, later filename, higher version number, or broader document does not automatically supersede the expected C0 source.

Supersession requires evidence and a founder decision.

### 4.5 Founder acceptance does not equal adoption or lock

Do not infer adoption or lock from:

* founder approval or acceptance;
* current repository placement;
* a document header;
* use by implementation work;
* references in companion registers;
* later RF work;
* apparent completeness; or
* inclusion in an evidence package.

## 7. Row-by-row recovery procedure

For each row, perform the following independently.

### Step 1: Search

Search every approved source location for:

* the exact filename;
* expected identifier;
* expected version;
* expected SHA-256;
* prior alternate filenames;
* known package paths;
* source references inside manifests; and
* repository history showing creation, movement, renaming, or replacement.

### Step 2: Hash

Calculate SHA-256 for every plausible source candidate.

Do not normalize line endings, encoding, whitespace, or metadata before calculating the raw-byte hash.

A normalized-content comparison may be performed separately, but it may not replace raw-byte hashing.

### Step 3: Preserve

Copy recovered candidates into a controlled evidence directory without modifying their bytes.

Use paths such as:

```text
track_c/<C0_ROW>/recovered_sources/
track_c/<C0_ROW>/current_repository_source/
track_c/<C0_ROW>/comparisons/
track_c/<C0_ROW>/provenance/
track_c/<C0_ROW>/decision_package/
```

### Step 4: Compare

Perform:

* raw-byte comparison;
* normalized-text comparison;
* heading and requirement comparison;
* identifier comparison;
* version comparison;
* authority-boundary comparison;
* requirement-ID comparison;
* founder-decision comparison;
* cross-reference comparison;
* dependency comparison;
* substantive semantic comparison; and
* formatting-only difference analysis.

### Step 5: Classify

Assign exactly one primary relationship classification:

* `EXACT_EXPECTED_SOURCE_RECOVERED_AND_CURRENT_BYTE_IDENTICAL`
* `EXACT_EXPECTED_SOURCE_RECOVERED_CURRENT_FORMATTING_DERIVATIVE`
* `EXACT_EXPECTED_SOURCE_RECOVERED_CURRENT_CORRECTED_SUCCESSOR_CANDIDATE`
* `EXACT_EXPECTED_SOURCE_RECOVERED_CURRENT_SUBSTANTIVE_SUCCESSOR_CANDIDATE`
* `EXACT_EXPECTED_SOURCE_RECOVERED_CURRENT_NONCONTROLLING_DERIVATIVE`
* `EXACT_EXPECTED_SOURCE_RECOVERED_CURRENT_CONFLICT`
* `EXPECTED_SOURCE_NOT_RECOVERED_BUT_PROVEN_SUCCESSOR_CANDIDATE_EXISTS`
* `EXPECTED_SOURCE_NOT_RECOVERED_AND_SUCCESSION_NOT_PROVEN`
* `MULTIPLE_CONFLICTING_SOURCE_CANDIDATES`
* `SOURCE_PROVENANCE_INSUFFICIENT`

Do not invent a hybrid classification merely to avoid identifying a conflict.

### Step 6: Recommend

For each row, recommend one founder decision:

* `CONFIRM_EXPECTED_C0_SOURCE_AS_CONTROLLING_ADOPTION_CANDIDATE`
* `CONFIRM_CURRENT_REPOSITORY_ARTIFACT_AS_FORMATTING_DERIVATIVE_ONLY`
* `CONFIRM_CURRENT_REPOSITORY_ARTIFACT_AS_CORRECTED_SUCCESSOR_CANDIDATE`
* `CONFIRM_CURRENT_REPOSITORY_ARTIFACT_AS_SUBSTANTIVE_SUCCESSOR_CANDIDATE`
* `PRESERVE_CURRENT_ARTIFACT_AS_NONCONTROLLING_DERIVATIVE`
* `RETURN_FOR_SUBSTANTIVE_FOUNDER_REVIEW`
* `DEFER_PENDING_ADDITIONAL_SOURCE_EVIDENCE`
* `REJECT_SOURCE_SUCCESSION_CLAIM`

A recommendation is not a founder decision.
