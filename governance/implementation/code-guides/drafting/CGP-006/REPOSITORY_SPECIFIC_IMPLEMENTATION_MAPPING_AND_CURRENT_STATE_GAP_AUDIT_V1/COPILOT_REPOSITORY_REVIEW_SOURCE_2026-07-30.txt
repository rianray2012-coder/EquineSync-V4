## Issues uncovered (prioritized)
1) README is essentially empty / placeholder
   - Why it matters: newcomers, contributors, or open-source users have no public project description, run/deploy guidance, or license.
   - Evidence: README.md contains only "Here are your Instructions".
   - Remedy: Add project summary, architecture overview, run instructions (backend/frontend), required env vars, license.

2) No LICENSE file
   - Why it matters: legal clarity for reuse/contributors.
   - Remedy: Add an appropriate LICENSE (MIT, Apache-2.0, etc.) at repo root.

3) backend/requirements.txt mixes runtime and dev tooling (black, flake8, mypy, pytest, bandit etc.) in one file
   - Why it matters: production installs (pip install -r requirements.txt) install unnecessary dev tools, slowing deploys and increasing attack surface.
   - Evidence: requirements.txt contains black, flake8, mypy, pytest, pycodestyle, pyflakes.
   - Remedy: Split into two files:
     - backend/requirements.txt (only runtime/prod deps)
     - backend/requirements-dev.txt (linters, test frameworks, dev-only libs)
   - Concrete change: remove dev packages from production requirements and update CI to install both when needed (CI should install dev deps only for lint/test steps).

4) CI missing dedicated static-analysis / dependency-audit / SCA / linter jobs
   - Why it matters: current CI runs tests and builds but does not fail PRs for linting, formatting, or known-vulnerability signals. Dependency vulnerabilities can slip through.
   - Evidence: .github/workflows/ci.yml only runs collect, backend tests with known-failure gate, and frontend build; linting/static scans are not present.
   - Remedy:
     - Add separate jobs for:
       - Python security scan (pip-audit or equivalent) and dependency update monitoring.
       - Node audit: npm audit --json and fail on severity > moderate (or create a report).
       - Run linters/formatters: black --check, ruff/flake8, mypy in a dedicated job.
       - Optionally add static security scans (bandit / SAST).
     - Use Dependabot or equivalent to open PRs for dependency updates.

5) Frontend dependency tree declares peer conflicts; CI uses --legacy-peer-deps
   - Why it matters: using --legacy-peer-deps silences peer-dependency mismatches rather than fixing them; it can hide incompatible or broken peer relationships (React 19 vs packages supporting React 18 mentioned in CI comment).
   - Evidence: CI comments and "npm ci --legacy-peer-deps".
   - Remedy:
     - Audit package.json for packages that pin/peer to React 18; upgrade or replace packages to be compatible with the chosen React version or pin Node/React to an intended supported combination.
     - Run npm ls to find conflicts, then update dependencies or move to resolutions/overrides if necessary.
     - As a short-term measure, add an automated "npm audit" step in CI and a dependency-lint job that fails the PR until peer issues are resolved.

6) Monorepo / large modules and single large files
   - Why it matters: very large files (task_engine.py ~48KB; many core/* modules are large) are harder to review, test, and maintain.
   - Remedy: Consider incremental refactor to split very large files into smaller modules with clearer responsibilities. Prioritize high-risk code paths (auth, billing, task engine).

7) Potential secret/API-key risk and env usage
   - Why it matters: repo may depend on secrets (Stripe, OpenAI/Google keys). Ensure no secrets are committed, and .env is not tracked.
   - Evidence: server.py loads .env; no .env file in repo listing (good) but must confirm no secrets are present in commit history.
   - Remedy:
     - Run a secrets scan (detect-secrets or GitHub secret scanning) on repo and history.
     - Add .env to .gitignore (frontend/backends already have .gitignore at frontend).
     - Add guidance in README about required environment vars (JWT_SECRET, MONGO_URL, STRIPE keys, SENDGRID/RESEND keys, etc.) and sample .env.example with non-sensitive placeholders.

8) No automated linter enforcement / style checks in CI
   - Why it matters: code style drift, type errors.
   - Remedy: Add a dedicated CI job that runs black --check, ruff or flake8, mypy --strict (or preferred flags) and fails the workflow on violations.

9) Large package-lock.json (frontend) committed
   - Why it matters: locks are normal, but large lockfiles should be kept up-to-date and vetted. Also, using package-lock for frontend is fine, but ensure npm version is controlled.
   - Remedy: Keep lockfile; run npm audit & npm ci in CI with a controlled Node version; consider adding automatic lockfile update PRs (Dependabot).

10) No top-level Dockerfile or standardized deployment instructions (unless elsewhere in docs)
    - Why it matters: deployment reproducibility.
    - Remedy: Add a Dockerfile and/or Deployment docs if you intend to deploy containers; otherwise add explicit deployment steps for Vercel (frontend) and backend hosting (e.g., container registry + k8s/Heroku/Serverless).
