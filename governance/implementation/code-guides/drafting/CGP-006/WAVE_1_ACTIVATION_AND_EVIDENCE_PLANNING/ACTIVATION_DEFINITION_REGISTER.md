
# CGP-006 Wave 1 Activation Definition Register

This register defines what future activation would mean for each guide and for the portfolio. The definitions are proposed planning records only.

## Portfolio Definition

Portfolio activation would be a future Founder governance event authorizing named governance actors to rely on `ES-CG-00`, `ES-CG-01`, `ES-CG-10`, and `ES-CG-13` as operative documentary standards for the approved scope. The recommended first stage is role-limited and planning-only.

Portfolio activation would not authorize implementation mapping, implementation, technical compliance claims, runtime operation, evidence fabrication, warning closure, GAP-0004 closure, source promotion, source-freeze amendment, or CGP-007.


## `ES-CG-00` - Code Guide Framework And Charter

**Proposed activation scope:** Code Guide lifecycle charter, authority boundaries, program custody, source-governance separation, and non-authorization rules.

**Actors permitted to rely after future activation:** Founder; Code Guide custodian; governance reviewer; evidence reviewer; future activation reviewer.

**Processes governed after future activation:** Guide lifecycle governance; authority-boundary review; package custody; source-lineage preservation.

**Obligations triggered by future activation:** Preserve lifecycle separation, enforce non-authorization language, maintain source custody, and carry warnings plus GAP-0004 without closure.

**Exclusions from activation:** Operational reliance, implementation mapping, implementation work, production use, source promotion, and warning or GAP closure.

**Prerequisites:** Founder activation decision; named accountable owner; warning carry-forward; GAP-0004 carry-forward; evidence custody; approved review cadence; exception/escalation path; suspension and deactivation rules.

**Evidence required before activation:** Activation directive, scope record, owner assignment, warning carry-forward record, GAP-0004 carry-forward record, source-integrity verification, package validation report.

**Evidence required after activation:** Monitoring records, review-cadence evidence, exception/escalation logs if any, suspension/deactivation records if triggered.

**Monitoring obligations:** Quarterly governance-custody review plus event-driven review after any successor activation, mapping, or source-governance directive.

**Review cadence:** `QUARTERLY_AND_EVENT_DRIVEN`

**Suspension conditions:** Suspend reliance if source custody fails, authority boundaries are weakened, warnings are omitted, or activation is represented as implementation authority.

**Withdrawal or deactivation conditions:** Founder withdrawal directive or failure of source custody, warning carry-forward, or GAP-0004 preservation.

**Dependencies on future authority:** Founder activation directive; separate implementation-mapping authority before any mapping; separate implementation authority before any implementation; separate runtime authority before runtime evidence.

**Readiness determination:** `READY_FOR_FOUNDER_ACTIVATION_CONSIDERATION_WITH_CONDITIONS`

## `ES-CG-01` - Engineering Authority And Precedence

**Proposed activation scope:** Engineering authority hierarchy, conflict treatment, exception escalation, and Founder precedence boundaries.

**Actors permitted to rely after future activation:** Founder; engineering authority reviewer; source custodian; governance reviewer; future exception reviewer.

**Processes governed after future activation:** Authority precedence review; conflict escalation; exception handling; cross-guide dependency review.

**Obligations triggered by future activation:** Keep authority precedence explicit, require separate authority for exceptions, and prevent contextual material from becoming normative by implication.

**Exclusions from activation:** Control-to-code mapping, ticket creation, source promotion, implementation sequencing, and runtime approval.

**Prerequisites:** Founder activation decision; named accountable owner; warning carry-forward; GAP-0004 carry-forward; evidence custody; approved review cadence; exception/escalation path; suspension and deactivation rules.

**Evidence required before activation:** Activation directive, scope record, owner assignment, warning carry-forward record, GAP-0004 carry-forward record, source-integrity verification, package validation report.

**Evidence required after activation:** Monitoring records, review-cadence evidence, exception/escalation logs if any, suspension/deactivation records if triggered.

**Monitoring obligations:** Quarterly authority-precedence review and immediate review after any source conflict, exception request, or successor mapping directive.

**Review cadence:** `QUARTERLY_AND_EVENT_DRIVEN`

**Suspension conditions:** Suspend reliance if conflict treatment is bypassed, exception authority is implied, or contextual sources are promoted without authority.

**Withdrawal or deactivation conditions:** Founder withdrawal directive or unresolved authority conflict affecting activated scope.

**Dependencies on future authority:** Founder activation directive; separate implementation-mapping authority before any mapping; separate implementation authority before any implementation; separate runtime authority before runtime evidence.

**Readiness determination:** `READY_FOR_FOUNDER_ACTIVATION_CONSIDERATION_WITH_CONDITIONS`

## `ES-CG-10` - Testing, Verification, And Assurance

**Proposed activation scope:** Documentary planning standards for future testing, verification, assurance evidence, false-pass prevention, and validation interpretation.

**Actors permitted to rely after future activation:** Founder; assurance reviewer; validation owner; evidence reviewer; future implementation-mapping reviewer.

**Processes governed after future activation:** Evidence-grade planning; validator design; assurance review; test-evidence acceptance planning.

**Obligations triggered by future activation:** Define evidence obligations without asserting technical conformance, preserve false-pass prevention, and require future authorized implementation and runtime evidence.

**Exclusions from activation:** Executing tests as implementation evidence, declaring code compliance, identifying technical targets, and treating CI success as activation.

**Prerequisites:** Founder activation decision; named accountable owner; warning carry-forward; GAP-0004 carry-forward; evidence custody; approved review cadence; exception/escalation path; suspension and deactivation rules.

**Evidence required before activation:** Activation directive, scope record, owner assignment, warning carry-forward record, GAP-0004 carry-forward record, source-integrity verification, package validation report.

**Evidence required after activation:** Monitoring records, review-cadence evidence, exception/escalation logs if any, suspension/deactivation records if triggered.

**Monitoring obligations:** Quarterly assurance-plan review and event-driven review after any implementation evidence or runtime evidence authority is issued.

**Review cadence:** `QUARTERLY_AND_EVENT_DRIVEN`

**Suspension conditions:** Suspend reliance if validators are treated as implementation proof, mandatory failures are skipped, or unverified evidence is marked verified.

**Withdrawal or deactivation conditions:** Founder withdrawal directive or validator/checksum failure affecting the activated scope.

**Dependencies on future authority:** Founder activation directive; separate implementation-mapping authority before any mapping; separate implementation authority before any implementation; separate runtime authority before runtime evidence.

**Readiness determination:** `READY_FOR_FOUNDER_ACTIVATION_CONSIDERATION_WITH_CONDITIONS`

## `ES-CG-13` - Completion, Evidence, And Traceability

**Proposed activation scope:** Completion boundaries, evidence grade, traceability, custody, closure, and activation-boundary governance.

**Actors permitted to rely after future activation:** Founder; evidence reviewer; traceability reviewer; package custodian; future activation owner.

**Processes governed after future activation:** Evidence custody; traceability review; closure-boundary review; activation-boundary review; package manifest control.

**Obligations triggered by future activation:** Keep completion distinct from activation, require verified evidence for satisfied statuses, and prevent premature closure of warnings or GAP-0004.

**Exclusions from activation:** Backdated activation, operational evidence fabrication, runtime operation, warning closure, and GAP-0004 closure.

**Prerequisites:** Founder activation decision; named accountable owner; warning carry-forward; GAP-0004 carry-forward; evidence custody; approved review cadence; exception/escalation path; suspension and deactivation rules.

**Evidence required before activation:** Activation directive, scope record, owner assignment, warning carry-forward record, GAP-0004 carry-forward record, source-integrity verification, package validation report.

**Evidence required after activation:** Monitoring records, review-cadence evidence, exception/escalation logs if any, suspension/deactivation records if triggered.

**Monitoring obligations:** Quarterly traceability and custody review plus immediate review after any checksum, manifest, evidence, or activation-scope change.

**Review cadence:** `QUARTERLY_AND_EVENT_DRIVEN`

**Suspension conditions:** Suspend reliance if evidence custody fails, traceability cannot be reproduced, or activation scope is expanded without Founder authority.

**Withdrawal or deactivation conditions:** Founder withdrawal directive or failure of traceability, manifest, checksum, or evidence-custody controls.

**Dependencies on future authority:** Founder activation directive; separate implementation-mapping authority before any mapping; separate implementation authority before any implementation; separate runtime authority before runtime evidence.

**Readiness determination:** `READY_FOR_FOUNDER_ACTIVATION_CONSIDERATION_WITH_CONDITIONS`
